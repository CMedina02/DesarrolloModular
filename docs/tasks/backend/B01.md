## 3. Funcionamiento técnico

Flutter envía solicitudes a Express bajo `/api/v1`. El inicio de sesión devuelve el JWT y el perfil. El servidor comprueba que la sesión siga activa y aplica el rol y el ámbito de empresa antes de acceder a PostgreSQL. Para Inventario también comprueba la activación del módulo.

Las operaciones de productos distinguen los campos editables de la existencia devuelta por la API. `POST /businesses/{business_id}/inventory/movements` recibe tres variantes según `movement_type`. Las entradas y salidas reciben una cantidad positiva. Los ajustes reciben la cantidad física contada y requieren un administrador. La salida y el ajuste requieren motivo. El servidor calcula el delta y toma el autor de la sesión. La transacción actualiza el stock y guarda el historial.

## 4. Decisiones de diseño

- Un proceso Express y un pool PostgreSQL compartido mantienen simple la instalación. Inventario conserva sus reglas y el Core concentra la identidad, los permisos y la configuración compartida.
- Las rutas de empresa expresan el ámbito de cada recurso. La ruta identifica la empresa solicitada y la sesión determina el acceso. `PLATFORM_ADMIN` administra la instalación. Los movimientos de Inventario requieren una cuenta con empresa, en coherencia con la relación SQL entre autor y movimiento.
- Precios y cantidades se intercambian como cadenas decimales. Las respuestas conservan dos y tres decimales respectivamente. El servidor aplica además las restricciones de unidad.
- Productos y cuentas se desactivan por estado para preservar sus referencias. Una categoría sin productos se puede eliminar. La unidad de un producto con movimientos permanece fija para conservar el significado del historial.
- Las tres operaciones de stock comparten una ruta y el mismo registro histórico. Cada variante conserva sus propios campos requeridos.

## 5. Pruebas

Se utilizó Redocly CLI 2.83.0 desde un directorio temporal. Los comandos, ejecutados desde la raíz del repositorio, fueron los siguientes.

```bash
/tmp/desarrollo-b01-validation/node_modules/.bin/redocly lint --extends minimal docs/api/openapi.yaml
/tmp/desarrollo-b01-validation/node_modules/.bin/redocly bundle docs/api/openapi.yaml --dereferenced --output /tmp/desarrollo-b01-validation/openapi-resolved.json
```

El primer comando validó el YAML y la estructura OpenAPI. El segundo generó el contrato con las referencias resueltas. Con Node.js se contrastaron los campos de los cinco recursos con `001_schema.sql`, los roles, las unidades, los tipos de movimiento y los límites de los patrones decimales. También se comprobó que los cuerpos de productos excluyen stock y empresa, que las escrituras de stock excluyen autor y delta, que salida y ajuste exigen motivo y que el ajuste requiere `ADMIN` según el contrato.

La verificación fue documental. La ejecución de solicitudes HTTP, la autorización efectiva y las transacciones se comprobarán al implementar las tareas correspondientes.

## 6. Explicación para el profesor

> Diseñamos un backend modular que se ejecuta como una sola aplicación. El Core identifica al usuario y delimita a qué empresa puede acceder. Inventario organiza el catálogo y define cómo cambiar existencias conservando un historial. Especificamos las solicitudes y respuestas en OpenAPI para desarrollar Flutter y Express en paralelo. Validamos el contrato con Redocly y contrastamos sus campos y restricciones con el esquema PostgreSQL existente.
