# B02 · Servidor Express y conexión PostgreSQL

## 1. Objetivo

Arrancar el backend, configurar su conexión con PostgreSQL y comprobar por HTTP si Express responde y si su base de datos está disponible.

## 3. Funcionamiento técnico

`npm start` carga `backend/.env` si existe y valida `HOST`, `PORT` y `DATABASE_URL`. Las variables ya definidas en el entorno tienen prioridad. El valor por defecto de `HOST` es `127.0.0.1` y el de `PORT` es `3000`. `DATABASE_URL` identifica el servidor y la base PostgreSQL. Si tu conexión requiere contraseña, agrégala en tu `.env` local y codifica los caracteres reservados de la URL. El archivo de ejemplo contiene únicamente valores de referencia.

| Ruta | Respuesta |
| --- | --- |
| `GET /health` | `200` y `{"status":"ok"}` si Express está atendiendo. |
| `GET /health/db` | `200` y `{"status":"ok"}` si `SELECT 1` se ejecuta. `503` con `DATABASE_UNAVAILABLE` cuando PostgreSQL no está disponible para la API. |

Ambas respuestas incluyen `Cache-Control: no-store`. Las rutas desconocidas devuelven `404` y los errores inesperados se traducen a `500` con el formato `{"error":{"code":"…","message":"…"}}` de B01. Las dos rutas de salud son operativas y se sirven en la raíz del servidor. Las rutas de negocio definidas en B01 usarán `/api/v1`.

El pool abre conexiones bajo demanda. El límite de espera para conseguir una conexión y el límite de la consulta de salud son de dos segundos cada uno. Cuando el proceso recibe `SIGINT` o `SIGTERM`, el servidor deja de aceptar conexiones y después cierra el pool.

## 4. Decisiones de diseño

- Separar la aplicación Express del arranque permite probarla por HTTP con una función de comprobación controlada. El proceso normal inyecta la consulta real de PostgreSQL.
- Un pool compartido reutiliza conexiones. La consulta `SELECT 1` verifica la comunicación con PostgreSQL sin depender de tablas ni modificar datos.
- Las comprobaciones separan dos problemas operativos. Si la base cae, Express puede seguir atendiendo `/health` y confirmar que el proceso HTTP funciona.
- La validación de configuración falla al inicio con un mensaje específico. La respuesta HTTP de error evita exponer detalles internos de la conexión.

## 5. Pruebas

Desde `backend/`, ejecutar:

```bash
npm ci
npm test
```

`npm test` pasó las siete pruebas con Node.js 26.13.1. Cubren las respuestas de salud con y sin conexión, una ruta desconocida y la validación de configuración.

La prueba de arranque usó el mismo comando de Node.js que `npm start` y una instancia temporal de PostgreSQL 18.7. `/health/db` devolvió `200` con PostgreSQL disponible y `503` al detener la instancia. Durante la caída, `/health` mantuvo el `200`. Al iniciar PostgreSQL de nuevo, `/health/db` volvió a `200` sin reiniciar Express. El proceso cerró con código `0` al recibir `SIGTERM`.

Para comprobar la configuración de una instalación, ejecutar `npm start` en una terminal y consultar estas rutas en otra:

```bash
curl -i http://127.0.0.1:3000/health
curl -i http://127.0.0.1:3000/health/db
```

La prueba de integración usó una instancia aislada. La conexión depende de las credenciales y la configuración de cada instalación.

## 6. Explicación para el profesor

> Inicializamos el servidor Express y configuramos un pool para reutilizar conexiones con PostgreSQL. Separamos las comprobaciones HTTP y de base de datos para saber dónde está una falla. Probamos las respuestas y verificamos con PostgreSQL real que Express sigue operativo durante una caída de la base y se reconecta cuando vuelve.
