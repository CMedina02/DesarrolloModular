# B03 · Primer administrador, autenticación y JWT

## 1. Objetivo

Inicializar el primer administrador de una instalación y permitir que el cliente inicie sesión y consulte su identidad mediante la API REST.

## 2. Implementación

| Archivo | Contenido |
| --- | --- |

| `backend/src/core/auth/routes.js`, `users.js` e `input.js` | Rutas, validación y consultas parametrizadas de autenticación. |
| `backend/src/core/auth/password.js` y `token.js` | Hash de contraseñas, emisión de JWT y verificación de sesiones. |

| [`docs/api/openapi.yaml`](../../api/openapi.yaml) | Contrato de sesión, duración del token y respuestas del inicio de sesión. |

## 3. Funcionamiento técnico

### Preparar la instalación

Configura `backend/.env` con `DATABASE_URL` apuntando a la base donde ya se instaló T02. Desde `backend/`, instala las dependencias con `npm ci`. Si en `.env` aún no hay una asignación de `JWT_SECRET`, genera una clave aleatoria y guárdala directamente en ese archivo:

```bash
node -e 'require("node:fs").appendFileSync(".env", "\nJWT_SECRET=" + require("node:crypto").randomBytes(32).toString("hex") + "\n", { mode: 0o600 })'
```

La API requiere una clave hexadecimal de 64 caracteres. Usa una clave distinta por instalación. Cambiarla invalida los JWT emitidos con la anterior.

### Crear el primer administrador

Usa un nombre y correo de la instalación y elige una contraseña de 15 a 256 caracteres. La CLI recibe la contraseña por entrada estándar. En Bash se puede leer sin mostrarla:

```bash
read -rs -p 'Contraseña del administrador: ' admin_password
printf '\n'
printf '%s\n' "$admin_password" | npm run bootstrap:admin -- "Nombre del administrador" "admin@example.com"
unset admin_password
```

En PowerShell 7.3 o posterior, `Read-Host -MaskInput` permite el mismo flujo:

```powershell
$adminPassword = Read-Host -Prompt 'Contraseña del administrador' -MaskInput
$adminPassword | npm run bootstrap:admin -- "Nombre del administrador" "admin@example.com"
Remove-Variable adminPassword
```

El comando guarda únicamente el hash. Antes de insertar, toma un bloqueo sobre `users` dentro de una transacción y comprueba si ya existe un `PLATFORM_ADMIN`, incluso inactivo. Las ejecuciones simultáneas quedan serializadas. El administrador tiene `business_id = NULL`. El índice único de T02 conserva la unicidad del correo sin distinguir mayúsculas.

### Iniciar sesión y consultar el perfil

Arranca Express con `npm start`. Envía el correo y la contraseña seleccionada como JSON en `POST /api/v1/auth/login`. El servidor busca el correo sin distinguir mayúsculas, verifica la contraseña y devuelve `access_token`, `token_type`, `expires_in` y `user`. El token dura 900 segundos y el perfil omite el hash.

Envía `Authorization: Bearer <token>` en `GET /api/v1/auth/me`. La API verifica la firma, el emisor, el destinatario, la vigencia y el UUID de la cuenta. Luego consulta el estado actual del usuario y, si tiene empresa, el de su empresa. Si cualquiera se desactiva, una consulta con ese JWT recibe `401`. Flutter puede usar el código `UNAUTHENTICATED` para volver al inicio de sesión y `Retry-After` para presentar la espera cuando recibe `429`.

## 4. Decisiones de diseño

- Las contraseñas se derivan con scrypt de Node.js, con una sal aleatoria por cuenta, costo `N = 2^15`, `r = 8`, `p = 3` y comparación de tiempo constante. Las cuentas ausentes o con un hash inválido también pasan por una derivación. [Guía de almacenamiento de contraseñas de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- El token firmado contiene el identificador y las marcas de tiempo de la sesión. El rol, la empresa y el estado se obtienen de PostgreSQL al consultar el perfil. Se utiliza `jose` para firma y verificación. [Documentación de jose](https://github.com/panva/jose).
- El inicio de sesión admite hasta 4 KiB de JSON sin compresión y limita las solicitudes a diez por IP por minuto. El contador se guarda en memoria de la instancia. La respuesta `401` es la misma para credenciales incorrectas, cuentas ausentes y cuentas o empresas inactivas. [Guía de autenticación de OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
- La inicialización es un comando local porque su acceso puede quedar bajo control del operador de la instalación. La transacción utiliza el esquema existente de T02.

## 5. Pruebas

Se ejecutó `npm test` desde `backend/` con Node.js 26.13.1. Pasaron 16 pruebas. Incluyen hashing y sales, credenciales inválidas, firma y expiración del JWT, límites del inicio de sesión, consulta del perfil y las comprobaciones de B02. `redocly lint --extends minimal docs/api/openapi.yaml` validó el contrato desde la raíz del repositorio.

La prueba de integración ejecutó la CLI y los endpoints contra una instancia temporal de PostgreSQL 18.7 con el esquema de T02. Se probaron el correo duplicado, la concurrencia del bootstrap y el rechazo de sesiones de cuentas o empresas desactivadas. Se utilizó la base temporal para aislar los datos de prueba.

## 6. Explicación para el profesor

> Creamos el primer administrador con una CLI que controla el acceso a la operación y evita duplicados incluso si se ejecuta dos veces al mismo tiempo. Guardamos un hash con sal en PostgreSQL. Después del inicio de sesión, Express emite un JWT de corta duración. Al consultar el perfil, valida ese token y comprueba si el usuario y su empresa siguen activos. Verificamos el flujo con pruebas automatizadas y una instancia real de PostgreSQL.
