# B05 · Seguridad y aislamiento multiempresa

## 1. Objetivo

Usar el contexto autenticado para delimitar cada operación administrativa y evitar que una escritura conserve permisos que se revocaron después de verificar su JWT.

## 3. Funcionamiento técnico

Express valida el JWT, consulta la cuenta actual y aplica el rol exigido por la operación. Para un usuario de empresa, la empresa autorizada se toma de esa cuenta. El UUID de la ruta debe coincidir. Para `PLATFORM_ADMIN`, las rutas que permiten ese rol definen la empresa por su UUID en la ruta. Las cabeceras adicionales, la consulta y el cuerpo carecen de autoridad para cambiar el ámbito.

El repositorio filtra la información por la empresa autorizada. Una actualización de usuario también usa el UUID del registro. Si actúa un `ADMIN`, la sentencia exige que el registro sea de un `EMPLOYEE`.

Las cuatro escrituras administrativas vuelven a leer y bloquear con `FOR SHARE` la cuenta del actor y, si aplica, su empresa. Si otra transacción está cambiando esos registros, PostgreSQL espera y devuelve el estado confirmado antes de que se ejecute la mutación. La comprobación y la escritura comparten conexión y transacción. [Aislamiento Read Committed de PostgreSQL](https://www.postgresql.org/docs/18/transaction-iso.html).

| Resultado | Respuesta |
| --- | --- |
| Cuenta o empresa inactiva, o sesión inválida | `401 UNAUTHENTICATED` |
| Rol insuficiente o cambiado durante una escritura | `403 FORBIDDEN` |
| Empresa fuera de alcance o registro sin acceso dentro de ella | `404 NOT_FOUND` |

## 4. Decisiones de diseño

- El control de ámbito se aplica antes de consultar los recursos solicitados. El repositorio recibe el UUID autorizado y usa parámetros SQL.
- El control transaccional mantiene la validación vigente hasta confirmar la escritura. La preparación del cuerpo y el cálculo del hash ocurren antes de tomar los bloqueos.
- Los listados validan la identidad y el alcance al inicio de la solicitud. Las mutaciones tienen una segunda comprobación porque cambian datos.
- El arranque del primer administrador utiliza el mismo manejo de transacciones y conserva su bloqueo de inicialización. Para B05 se usó el esquema existente de T02.

## 5. Pruebas

`npm test`, ejecutado desde `backend/`, pasó 26 pruebas. Los casos de B05 cubren el ámbito frente a cabeceras y parámetros ajenos a la sesión, la revocación antes de escribir, el uso de la misma conexión durante la mutación, el rollback y el descarte de una conexión si la reversión falla.

En una instancia temporal de PostgreSQL 18.7 se ejecutaron las siete operaciones de B04 con dos empresas. Se mantuvieron abiertas transacciones que cambiaban el rol del actor y desactivaban su empresa, y se verificó que sendas solicitudes HTTP esperaran por el bloqueo. Tras confirmar los cambios, la API devolvió `403` y `401`, respectivamente. Ambos intentos conservaron intacto al usuario que se quería editar. También se repitió la prueba de inicialización de B03 y dos ejecuciones simultáneas siguieron creando un solo administrador.

`redocly lint --extends minimal docs/api/openapi.yaml` validó el contrato desde la raíz del repositorio.

## 6. Explicación para el profesor

> El token identifica al usuario. A partir de esa identidad, Express consulta su rol y la empresa que puede usar. Un UUID en la ruta solo selecciona información dentro de ese permiso. Para las escrituras, PostgreSQL vuelve a comprobar la autorización y mantiene los registros bloqueados hasta que termine la transacción. Probamos solicitudes simultáneas y comprobamos que una revocación ya confirmada impide la modificación.
