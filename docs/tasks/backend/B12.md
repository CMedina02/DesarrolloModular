# B12 · Instalación, configuración y migraciones

## 1. Objetivo

Preparar una instalación reproducible del backend de Inventario. Una instalación nueva debe poder aplicar el esquema y arrancar la API. Una base preparada con T02 debe poder incorporar el registro de migraciones conservando sus datos.

## 2. Implementación

| Archivo | Contenido |
| --- | --- |
| `backend/database/migrate.js` y `legacy-schema.js` | Orden de migraciones, firmas, transacción y verificación para adoptar instalaciones previas. |
| `backend/scripts/migrate.js` y `backend/package.json` | Comando de migración y ejecución de la suite de integración. |
| `backend/integration/database.js`, `harness.js` y `migrations.integration.js` | Esquemas aislados y pruebas del mismo migrador que usa el comando. |
| [README](../../../README.md) y [guía de base de datos](../../../backend/database/README.md) | Puntos de entrada para instalar, arrancar y probar. |

## 3. Instalar o actualizar

### Preparar la conexión

Requiere Node.js 22.21 o posterior y PostgreSQL con `gen_random_uuid()` disponible. Selecciona una base PostgreSQL para la instalación y usa una cuenta con permiso para crear los objetos del esquema de aplicación. Para crear una base y cuenta nuevas, ejecuta con una cuenta administradora de PostgreSQL:

```bash
createuser --pwprompt inventario_app
createdb --owner=inventario_app inventario_comercial
```

Si la base o la cuenta ya existen, usa las correspondientes a la instalación. Desde `backend/`, ejecuta `npm ci`. Si todavía falta `.env`, prepáralo a partir de `.env.example`. Configura `DATABASE_URL` con la conexión correcta y genera `JWT_SECRET` según B03. El valor de ejemplo de `HOST` es `127.0.0.1` y el de `PORT` es `3000`. [Configuración de B03](B03.md)

### Aplicar las migraciones

**Base vacía.** Desde `backend/`, ejecuta:

```bash
npm run migrate
```

**Base preparada manualmente con T02 o T02 y B06.** Tras confirmar que se utilizaron los scripts oficiales, ejecuta:

```bash
npm run migrate -- --adopt-existing
```

El comando comprueba que estén las tablas, columnas y protecciones de catálogo esperadas. Marca las versiones existentes y aplica las que faltan. Si detecta una estructura incompleta o un historial incompatible, termina con error y revierte el lote. Para actualizaciones posteriores, usa `npm run migrate`.

### Arrancar y verificar

1. Si aún falta el primer `PLATFORM_ADMIN`, créalo mediante `npm run bootstrap:admin` siguiendo el procedimiento de entrada segura de B03. [Inicialización de B03](B03.md)
2. Ejecuta `npm start` desde `backend/`.
3. Desde otra terminal, comprueba `GET /health` y `GET /health/db`. Con la configuración de ejemplo, ambas rutas están en `http://127.0.0.1:3000` y responden `200` cuando Express y PostgreSQL están disponibles.
4. Inicia sesión como `PLATFORM_ADMIN`. Crea o identifica una empresa activa, habilita Inventario para ella y prepara las cuentas de empresa. Las operaciones están en [OpenAPI](../../api/openapi.yaml) y la activación se explica en [B06](B06.md).

## 4. Decisiones de diseño

- `desarrollomodular_schema_migrations` registra cada versión y la firma SHA-256 de su archivo. La firma normaliza los saltos de línea de Windows y Linux. Si cambia un archivo aplicado, agrega una nueva migración versionada para resolver el cambio.
- El migrador usa el esquema activo de PostgreSQL y mantiene el bloqueo de migración durante la transacción. Una ejecución concurrente espera, relee el historial confirmado y aplica solo las versiones pendientes. [Bloqueos de PostgreSQL](https://www.postgresql.org/docs/18/explicit-locking.html)
- El lote de migraciones confirma sus cambios y el historial juntos. `001_schema.sql` inicia el esquema y los archivos de `backend/database/migrations/` se leen por versión. Conserva un solo `BEGIN` y `COMMIT` de envoltura por archivo y deja al migrador el control de la transacción.
- Los datos demo y las pruebas SQL se ejecutan aparte, sobre una base de desarrollo. [Guía de base de datos](../../../backend/database/README.md)

## 5. Pruebas

Se ejecutó `npm test` y pasaron las 42 pruebas rápidas. `npm run test:integration` se ejecuta con una base PostgreSQL de pruebas configurada mediante `INTEGRATION_DATABASE_URL`, según [B11](B11.md). La suite completa pasó dos veces en PostgreSQL 18.7 temporal. El ejecutor reportó 13 pruebas por ejecución, incluidos los dos casos padre. Tras cada ejecución se retiraron los esquemas de prueba y se conservó una tabla de control externa.

En otra instancia temporal vacía, se ejecutó `npm run migrate` dos veces y se arrancó con `npm start`. La segunda ejecución informó que la base estaba al día. `/health` y `/health/db` devolvieron `200`.

| Caso de migración | Resultado observado |
| --- | --- |
| Base vacía y dos ejecuciones concurrentes | Las versiones se aplican una vez y la siguiente ejecución informa que está al día. |
| T02 previo | Se registra T02 y se aplica B06 conservando los datos. |
| T02 y B06 previos | Se registran ambos y se conserva el estado del módulo. |
| Estructura parcial | Se rechaza y se conserva el esquema previo. |
| Fallo durante una migración | El lote y el historial se revierten juntos. |
| Firma alterada | El migrador detecta la discrepancia y detiene la ejecución. |

## 6. Explicación para el profesor

> El comando prepara la base según las versiones registradas. Si dos personas intentan migrar al mismo tiempo, PostgreSQL serializa la operación. Probamos una instalación nueva, otra que ya tenía T02 y un fallo en mitad de una migración. El historial de versiones y los cambios de la base se confirman juntos.

## 7. Alcance de la entrega

B12 cierra la instalación del backend. El despliegue en el entorno compartido y la validación desde Flutter corresponden a la integración del equipo.
